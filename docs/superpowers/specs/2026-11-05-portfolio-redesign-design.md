# bonghee 포트폴리오 사이트 전면 개편 — 설계

작성일: 2026-11-05 · 레포: `hae8064/bonghee` (develop) · 배포: Vercel (`bonghee.vercel.app`)

## 1. 의도와 이유

지금 사이트는 2026년 초 기준이라 "풀스택 개발자 / 솔루션서비스팀 팀장", 옛 수치(API 2초 → 0.25초), 이미 뺀 프로젝트(뉴스 요약)가 앞에 나온다. 그사이 이력서와 PDF 포트폴리오(`~/leo/포폴_2026/이봉희 포트폴리오.pptx`, 16장)는 **"백엔드 / 클라우드 엔지니어"**로 방향을 바꿨고, 사용자가 이 pptx를 지금까지 중 가장 마음에 들어 한다. 사이트를 이 pptx 내용에 맞춰 다시 만든다.

동시에 사용자는 **프론트 실력도 보여 주고 싶다.** 직무 간판은 백엔드/클라우드로 두고, 프론트 실력은 문장이 아니라 사이트 자체(3D·애니메이션·인터랙티브 다이어그램)로 증명한다. 효과는 장식이 아니라 **설계를 설명하는 데** 쓴다 — 요청이 서비스 사이를 오가는 흐름을 직접 보여 주는 식.

보는 사람: 채용 담당자가 먼저(첫 3초에 인상), 백엔드 면접관이 다음(사례를 깊게 읽음).

## 2. 목표 / 비목표 / 실패 조건

목표
- 첫 화면에서 "이 사람은 다르다"는 인상 (3D 아키텍처 히어로)
- 설계 사례 4개를 흐름도 애니메이션으로 이해시키기: Qanti 아키텍처, 병원 미들웨어 SSO, Sectra Grid-Split, 동적 타일 서빙
- 내용이 PDF 포트폴리오·이력서와 어긋나지 않음

비목표
- 블로그, CMS, 다국어, 다크/라이트 토글
- 이력서 PDF 자동 생성(기존 `/pdf`, `/ppt` 페이지와 `utils/generatePPT.ts`는 제거 대상)

실패 조건 (기술적으로 돌아가도 실패)
- 효과 때문에 내용이 안 읽힘, 또는 첫 화면이 3초 넘게 비어 있음
- pptx에 없는 사실을 지어냄. 특히 동적 타일 서빙에서 "Rust로 바꿔서 빨라졌다"고 쓰는 것(속도는 스케줄링·256 타일이 만들었고 Rust는 격리 목적). 역할은 "단독/혼자"로 쓰지 않고 표기 없이 작업만 기술(pptx와 동일).
- 병원 실명 노출 (pptx 원칙과 동일: "병원 미들웨어", "상급종합병원" 같은 일반 표현만)
- 모바일에서 가로 스크롤 생기거나 3D 때문에 버벅임

## 3. 제약

- 스택 유지: Next.js 15 (App Router) + React 19 + TypeScript + Tailwind 4, Vercel 배포. `react-icons` 유지 가능, `framer-motion`은 필요 없으면 제거.
- 추가 라이브러리: `three` + `@react-three/fiber` (+ 필요시 `@react-three/drei`), `animejs`. 버전은 빌더가 고르되 고정.
- 접근성: `prefers-reduced-motion`이면 애니메이션 없이 완성된 정지 화면. 다이어그램은 SVG + 텍스트라 스크린리더/검색에도 읽힘.
- 성능: three.js는 클라이언트 전용 동적 import, 히어로 밖으로 스크롤하면 렌더 루프 정지. 모바일(<768px)은 노드·파티클 수를 줄이거나 정지 이미지로 대체.
- 공개 사이트라 **전화번호는 싣지 않는다** (이메일, GitHub만).
- 작업은 새 브랜치 → 로컬 확인 → PR → Vercel 프리뷰 확인 → 사용자 승인 후 머지. 커밋은 사용자 요청 시에만.

## 4. 사용자가 정한 것

### 시각 방향 (브라우저 시안에서 선택)
- **첫 화면 = A "살아 있는 아키텍처":** 짙은 네이비 배경, three.js로 실제 서비스 노드(Browser, Nginx, Analysis, IMS, MongoDB, AI Worker, S3 등)가 3D로 떠 있고 요청이 빛 입자로 간선을 따라 흐름. 마우스에 따라 회전. 왼쪽에 이름·직무·한 줄 소개.
- **다이어그램 = C "요청 추적":** 터미널 톤(짙은 배경, 초록 계열 선, 모노스페이스 라벨). 스크롤이 닿으면 선이 그려지고 패킷이 노드 사이를 이동. anime.js 타임라인 + SVG.

### 사례 01 — Qanti 병리 IHC 분석 플랫폼 (pptx 7, 8, 11쪽)
- 담당: 백엔드 설계, 병원 연동 API, 인증 설계, 인프라 (3인 팀) · 2023.08–현재
- **흐름도 필수:** 스캐너(WSI, SVS/MRXS) → 수집(공유폴더 감시, CIFS + cron) → API(업로드 접수, Spring Boot) → 큐(SQS / RabbitMQ) → 추론(GPU 컨테이너, FastAPI·CUDA) → 저장(MongoDB) → 뷰어. 슬라이드 패킷이 흐름.
- **[ Cloud | 폐쇄망 ] 토글:** 같은 파이프라인에서 부품만 바뀌는 모핑 애니메이션 (pptx 11쪽 표 그대로)
  - 이미지 전달: ECR pull·태그 교체 ↔ tar save·암호화 전송·load
  - 오케스트레이션: ECS/EKS 롤링, ArgoCD GitOps ↔ 서버실 GPU 서버 직접 구성 (RTX A5000, 4080S)
  - 큐: AWS SQS ↔ RabbitMQ
  - 관측: CloudWatch ↔ Prometheus · Grafana · Loki
  - 공통: 소스에서 빌드한 Docker 이미지 하나, 태그로 버전 고정 → 재빌드 없이 모델 교체·롤백
- **현장 구축도 "약간" 어필** (사용자 결정): 폐쇄망 쪽에 "상급종합병원 중심 10곳 이상 서버실 직접 구축·운영"과 자동 업데이트 차단·드라이버 버전 고정·이미지 암호화 반입을 설정·스크립트로 고정한 점을 넣는다. 단 주제는 어디까지나 "한 이미지를 두 환경에 배포하는 설계"이고, 현장 구축이 첫 문장이 되지는 않는다.
- 상세에 들어갈 다른 내용: 서비스 개요 표(분석 대상 HER2·Ki-67·ER·PR, 1건당 2GB 이상, 결과 수십만~수백만 건), 뷰어 스크린샷/데모 영상(`public/videos/aivis-demo-compressed.mp4` 재사용 가능), 큐 기반 업로드 분산(WebSocket 진행률, Redis 캐싱, 동시 업로드 중 서버 다운 0건), 외부 연동(EMR/LIS/PACS, Sectra·INFINITT·Philips IMS, OCS Polling/Callback 이중 규격).

### 사례 02 — 병원 미들웨어 SSO (pptx 5, 6쪽, 사용자 본인 커밋 확인됨)
- 시퀀스: 병원 미들웨어 / 브라우저 / 분석 서버 / IMS(인증) 네 열, ①~⑧
  ① 티켓 발급 JWT·60초·jti → ② 티켓을 URL에 담아 진입 → ③ 티켓 중계 → ④ 서명·만료·jti·slideId 검증, 사번 계정 조회(없으면 생성) → ⑤ 30초 일회용 code → ⑥ 302 리다이렉트(code) → ⑦ code를 POST로 교환 → ⑧ 세션 토큰(응답 본문)

- 한계: 공유 ROI 데이터는 누가 그렸는지 남지 않음

### 사례 03 — Sectra 결과 Grid-Split (Obsidian `Sectra/Grid-Split 성능 최적화.md`, 사용자 작업으로 확인)
- 문제: Sectra 뷰어로 보내는 결과 content JSON이 172MB~1.9GB, 첫 렌더 때 전체 파싱
- 조치: ① 업로드 시점에 MVT → Sectra 형식 사전 변환(hook 시점 변환 제거) ② 좌표를 10×10 coarse grid로 분할 파일 생성(`{cgx}_{cgy}.json`), ROI가 걸치는 칸만 로드 ③ 로드 후 shapely prepared로 ROI polygon 내부 cell만 정밀 필터 ④ orjson 파싱. 로딩 우선순위: 메모리 캐시 → 분할 파일 → 전체 JSON(fallback)
- 결과(실측만): 172MB · 243,717 cells 기준 첫 렌더 1,618ms → 607ms (~2.7배). 예: 172MB 중 12개 파일 20MB만 로드
- **1.9GB 수치는 측정값이 없으므로 "파일 크기 범위"로만 언급, 속도 수치 금지**
- 한계: 세로로 긴 이미지는 Y > 1.0이라 clamping 필요, 캐시 히트 시 차이 없음, 기존 슬라이드 878개 재변환 필요
- 다이어그램: 왼쪽 "1.9GB 한 덩어리 통째로", 오른쪽 10×10 격자 위에 ROI를 그리면 걸치는 칸만 점등 → 그 칸만 패킷으로 이동

### 사례 04 — 동적 타일 서빙 (pptx 8, 9, 10쪽 그대로)
- 원본 WSI에서 요청 시점에 타일을 잘라 보내는 경로. 역할 표기 없이 작업만 기술.
- 이전 구조: 뷰어 → Next 프록시 → IMS(JVM) → JNI → Philips SDK, 한 프로세스. 줌·이동 한 번에 타일 요청이 최대 약 1,000개 몰려도 순서·취소 없이 모두 디코딩해 실패 175건, 1024 타일이라 장당 비용 큼, SDK가 네이티브에서 죽으면 IMS 전체 다운.
- 이후 구조: 뷰어 → IMS(JVM) → Rust 워커(별도 프로세스: 캐시 확인 · 같은 타일 합치기 · 큐·stale 취소) → Philips SDK. 256 PNG, 프록시 없이 직접 요청, 10초 마감 넘기면 워커만 종료 후 다음 요청에서 재기동.
- 단계별 p95(뷰어 측정): 1008ms → 310ms(요청 스케줄링·stale 취소, 실패 175→0) → 99ms(256 PNG·뷰어 캐시) → 97ms(Rust 워커 전환)
- 반드시 지킬 문구: 속도를 만든 건 스케줄링과 256 타일, Rust 전환은 99→97ms로 거의 차이 없음 — 목적은 장애 격리.
- 한계: 오래 이동·줌하면 p95 143ms, 최대 1.7초 spike. 구간별 계측(Server-Timing)이 다음 과제.
- 다이어그램: 이전/이후 구조를 나란히(C 스타일), 이전 쪽은 요청 패킷이 몰려 일부 빨간 실패, 이후 쪽은 화면 밖 요청이 회색으로 취소되고 같은 타일 요청이 하나로 합쳐짐. 아래에 단계별 p95 막대가 스크롤에 맞춰 줄어듦.

### 숫자 띠 (실측만)
- cell-group 조회 평균 1.78s → 0.26s (Motor 전환·Aggregation·Compound Index)
- 처리량 25 → 187 req/s (autocannon 동시 50)
- Sectra 172MB JSON 첫 렌더 1.6s → 0.6s
- 뷰어 첫 렌더(세포 19만 개) 5s → 1s 이내 (WebGL 벡터 레이어 + Worker 안 R-tree)
- 동적 타일 서빙 p95 1008ms → 97ms, 실패 175 → 0건

## 5. 내 판단으로 정한 것 (사용자 확인 전)
- 사이트 전체 배경을 짙은 네이비 하나로 통일 (A·C 둘 다 어두움). 서체 Noto Sans KR + 모노스페이스(JetBrains Mono 등), 강조색 네이비/블루 + 다이어그램 초록.
- 효과는 첫 화면·다이어그램·숫자·프로젝트 카드에만. 경력·기술·학력은 읽기 위주.
- 모바일 다이어그램은 세로 배치.
- 공개 사이트에서 전화번호 제외.
- 라이즈이엔엠 인턴 경력, 중고차·부트캠프 프로젝트 제외 (pptx와 동일).
- **프로젝트 카드 내용과 클릭 동작:** 상세 페이지는 만들지 않는다. 카드에 pptx 12·13쪽 요약(기간·역할·핵심 3줄·기술)을 싣고, 링크는 외부로만 — 워크유 `worku.kr`, 공감블라인드 `construction.gonggamblind.com` + `github.com/hae8064/gonggamBlind`. dev-reader는 pptx 12쪽 행("RSS 개발 아티클을 문장 단위로 나누고 단어 뜻을 미리 뽑아 두는 개인용 리더. 기사별 뜻과 전역 단어장 분리 설계", Next.js·NestJS·TypeORM·PostgreSQL·Gemini·DeepL, 2026.09–10, 개인)을 쓰고, 레포가 private이라 링크 없음.
- **배포 흐름:** 지금 `.github/workflows/deploy.yml`은 develop으로 PR이 머지되면 바로 `--prod` 배포하고 프리뷰 단계가 없다. 그래서 작업 브랜치는 develop에서 따고, 머지 전에 로컬 `pnpm build && pnpm start`로 확인한 뒤, 필요하면 `vercel deploy`(prod 아님)로 프리뷰 URL을 수동으로 띄워 사용자에게 보여 준다. CI의 Node 18 / pnpm 8은 새 의존성에 맞게 올린다(Node 20 이상).
